# 03 — 创建任务使用百度沙箱执行

**状态**：Implemented MVP（下载/执行已打通，真实 push 仍待收口）  
**记录时间**：2026-06-02 10:18:03 +0800
**最近更新**：2026-06-03 01:10:00 +0800

## 1. 背景

当前 Wegent 创建代码任务时，`ClaudeCode` / `Agno` 等本地执行型 Shell 默认通过 Executor Manager 创建 Docker 容器执行任务。

百度内网场景希望将任务执行环境切换为百度 Agent Sandbox：

- 使用百度托管沙箱替代本地 Docker 容器
- 通过 `ducc` 在沙箱内提交任务和追问
- 使用百度内网身份、icode 权限和 DevOps 工具链
- 保留 Wegent 当前任务创建、消息展示、回调和运行状态管理体验

Phase 1 探活已确认：

- `code-agent` 模板可以创建沙箱并执行命令
- 沙箱内包含 `ducc`
- 写入 `/root/.baidu-cc/user.json` 后，`ducc -p` 可成功回答问题
- 浏览器数据面泛域名访问仍有 `502` 问题，需继续确认端口暴露机制

## 2. 需求目标

明确这次要解决什么，不解决什么。

本次 MVP 已解决：

1. Wegent 创建任务时可以路由到百度 Agent Sandbox 执行。
2. Executor Manager 新增 `baidu_sandbox` 执行器，与现有 `docker` 执行器并存。
3. 创建沙箱后自动写入 DUCC 配置文件 `/root/.baidu-cc/user.json`。
4. 初期任务派发通过 `ducc -p` 非交互提问完成，并将输出回传给 Backend。
5. 保留任务级配置开关，支持按 `ExecutionRequest.executor_type` 或全局 `EXECUTOR_DISPATCHER_MODE` 选择 Docker / 百度沙箱。
6. 新增 `Shell.spec.executorType`，公共 Shell `BaiduSandbox` 可通过 `executorType=baidu_sandbox` 自动触发百度沙箱执行。
7. 同一个任务后续追问可复用 `baidu-sandbox-{sandbox_id}`，避免每轮都创建新沙箱。

本次不解决：

1. 不一次性替换所有 Docker 执行器。
2. 不实现浏览器预览 iframe 的最终产品化；端口暴露仍作为独立阻塞项跟进。
3. 不重构登录系统为完整 UUAP 主登录。
4. 不把任何沙箱 API Key、个人 token、模型 token 写入代码或文档。

## 3. 方案选择

采用“新增执行器 + 配置路由”方案。

### 方案 A：全局切换

通过 `EXECUTOR_DISPATCHER_MODE=baidu_sandbox` 将所有本地执行型任务切到百度沙箱。

优点：实现简单，验证快。  
缺点：回归面大，Docker 本地开发能力会受影响。

### 方案 B：按任务 / Shell 显式选择

保留 Docker 默认执行器，通过任务 metadata、Shell spec 或环境配置选择 `executor_type=baidu_sandbox`。

优点：可灰度、可回滚、便于对比验证。  
缺点：需要在 Backend 请求构建和前端/配置入口增加字段。

### 推荐

先采用方案 B，并保留方案 A 作为内网部署的全局开关。

## 4. 数据设计 / 接口影响

如果涉及数据结构、接口、配置项或持久化，写清楚：

### 配置项

Executor Manager：

- `BAIDU_SANDBOX_API_KEY`：百度沙箱控制面 API Key
- `BAIDU_SANDBOX_DOMAIN`：默认 `agent-sandbox.baidu-int.com`
- `BAIDU_SANDBOX_TEMPLATE`：默认 `code-agent`
- `BAIDU_SANDBOX_TIMEOUT`：沙箱生命周期，默认 `600`
- `BAIDU_SANDBOX_DUCC_TIMEOUT`：单次 DUCC 命令超时，默认 `300`
- `BAIDU_CC_MODEL_TOKEN` / `ANTHROPIC_AUTH_TOKEN`：DUCC 模型 token
- `EXECUTOR_CONFIG`：增加 `baidu_sandbox` 执行器 import path
- `EXECUTOR_DISPATCHER_MODE`：可全局切换为 `baidu_sandbox`

本地 `./start.sh` 启动时已显式透传以下百度沙箱相关环境变量到 Executor Manager：

```text
BAIDU_SANDBOX_API_KEY
BAIDU_SANDBOX_ACCESS_TOKEN
BAIDU_SANDBOX_DOMAIN
BAIDU_SANDBOX_TEMPLATE
BAIDU_SANDBOX_TIMEOUT
BAIDU_SANDBOX_DUCC_TIMEOUT
BAIDU_CC_MODEL_TOKEN
ANTHROPIC_AUTH_TOKEN
UGATE_TOKEN
UUAP_ACCESS_TOKEN
EXECUTOR_DISPATCHER_MODE
EXECUTOR_CONFIG
```

如果任务失败并提示 `Baidu Sandbox DUCC model token is missing`，说明任务已经进入 `BaiduSandboxExecutor`，但 Executor Manager 进程没有拿到 `BAIDU_CC_MODEL_TOKEN` 或 `ANTHROPIC_AUTH_TOKEN`。

正式上线时同样必须在部署层把这些值注入到 `executor_manager` 服务。当前 `docker-compose.yml` 已增加对应环境变量映射，生产环境应通过平台 Secret、K8s Secret 或受控 `.env` 注入真实值，不能把真实 token 写入代码仓库。

Backend / Task：

- `ExecutionRequest.executor_type` 已存在，可用于传递 `baidu_sandbox`
- `Shell.spec.executorType` 已新增，可配置为 `baidu_sandbox`
- 公共 Shell 种子数据已新增 `BaiduSandbox`，其 `shellType` 仍为 `ClaudeCode`，实际执行器由 `executorType=baidu_sandbox` 决定
- `sandbox_metadata.template` / `BAIDU_SANDBOX_TEMPLATE` 用于指定百度沙箱模板
- 可选扩展用户 token 字段：加密存储百度个人 access token 和 DUCC 模型 token

### 不落库的短期方案

短期使用环境变量完成内网验证：

- 沙箱 API Key：部署环境变量
- 个人 access token：从用户 git_info / ugate token 或内部 token provider 获取
- DUCC 模型 token：部署环境变量

### 长期方案

Backend 加密存储用户级百度 token，Executor Manager 通过内部接口按 `user_id` 拉取：

- `/api/internal/users/{user_id}/baidu-token`
- `/api/internal/users/{user_id}/baidu-cc-model-token`

## 6. 后端行为

### 6.1 Backend 请求构建

`backend/app/services/execution/request_builder.py` 已构建 `ExecutionRequest`。

已增加执行器选择逻辑：

- 默认沿用现有 Docker
- 当 Shell 配置 `spec.executorType = "baidu_sandbox"` 时，设置 `request.executor_type = "baidu_sandbox"`
- 保留 `executor_type` 显式覆盖能力
- Backend 执行路由在存在 `executor_type` 时强制走 Executor Manager HTTP callback，避免 standalone/in-process 模式误走本地执行

### 6.2 Executor Manager 执行器

已新增目录：

```text
executor_manager/executors/baidu_sandbox/
├── __init__.py
├── client.py          # E2B-compatible SDK wrapper
├── executor.py        # BaiduSandboxExecutor
├── token_provider.py  # env/task token resolution
└── ducc_config.py     # /root/.baidu-cc/user.json builder
```

核心职责：

1. `submit_executor()`：创建百度沙箱，写 DUCC 配置，派发首个任务
2. `create_instance()`：调用 `Sandbox(template=..., metadata=..., envs=...)`
3. `wait_instance_ready()`：通过 `echo ready` 命令探测沙箱可用
4. `dispatch_task_to_instance()`：执行 `ducc -p <prompt> --output-format text`
5. `delete_executor()`：通过 `Sandbox(sandbox_id=...).kill()`
6. `get_container_status()`：将百度沙箱状态映射成 Wegent status
7. 如果请求已有 `executor_name=baidu-sandbox-{sandbox_id}`，复用既有沙箱继续执行 DUCC

当前 executor name 约定：

```text
baidu-sandbox-{sandbox_id}
```

这样取消任务或清理时可以从 `executor_name` 反解真实百度 `sandbox_id`。

### 6.3 DUCC 任务派发

创建后写入：

```json
{
  "env": {
    "ANTHROPIC_AUTH_TOKEN": "<from token provider>",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "auto",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "auto",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "auto",
    "ANTHROPIC_MODEL": "auto",
    "DISABLE_BAIDU_CLAUDE_UPDATE": "1"
  }
}
```

派发命令：

```bash
ducc -p '<task prompt>' --output-format text
```

首期可以同步执行并回传最终结果；后续再做 stream-json 流式输出。

### 6.4 回调与消息

已复用 Backend 当前 `/api/internal/callback` 语义：

- DUCC stdout：通过 `response.output_text.delta` 写入 assistant message
- 执行成功：通过 `response.completed` 完成任务
- 执行失败：通过 `error` event 标记失败，附带错误原因

如果 DUCC 输出包含 warning，如 `COMATE_AUTH_TOKEN 403`，但 exit code 为 0，则不标记任务失败。

## 7. 启用方式

### 7.1 按单个任务启用

构建 `ExecutionRequest` 时设置：

```json
{
  "executor_type": "baidu_sandbox",
  "sandbox_metadata": {
    "template": "code-agent",
    "timeout": 600
  }
}
```

### 7.2 通过公共 Shell 启用

初始化公共资源后选择 `BaiduSandbox` Shell 创建 Agent。

公共 Shell 配置：

```yaml
spec:
  shellType: ClaudeCode
  executorType: baidu_sandbox
```

任务构建时 Backend 会自动把 `executorType` 转成 `ExecutionRequest.executor_type`。

### 7.3 全局启用

部署 Executor Manager 时设置：

```bash
EXECUTOR_DISPATCHER_MODE=baidu_sandbox
```

默认 `EXECUTOR_CONFIG` 已包含：

```json
{
  "docker": "executor_manager.executors.docker.DockerExecutor",
  "baidu_sandbox": "executor_manager.executors.baidu_sandbox.BaiduSandboxExecutor"
}
```
